# Перевод документации

[English](../en/translating.md) · **Русский**

На этой странице описано, как добавить язык документации и как поддерживать
перевод в актуальном состоянии. Здесь же описано, как добавить в skill
правила для нового языка. Страница предназначена для переводчиков,
рецензентов и мейнтейнера проекта.

Носители языков могут помочь двумя способами:

- перевести документацию (основная часть этой страницы);
- написать или проверить языковой файл skill (см.
  [Языковые правила для skill](#языковые-правила-для-skill)).

Исходный язык документации — английский. Английские файлы — эталон для всех
переводов. Первый черновик перевода делает AI-модель. Затем черновик
проверяют носители языка. После проверки мейнтейнер публикует перевод.

## Роли

| Роль | Кто | Задачи |
| --- | --- | --- |
| Автор запроса | Любой человек | Просит добавить новый язык. |
| Переводчик | Любой человек | Делает черновик с помощью AI-модели или вручную. Обновляет перевод, когда меняется английский оригинал. |
| Рецензент | Носитель языка | Сравнивает перевод с английским оригиналом. Одобряет перевод или предлагает изменения. |
| Мейнтейнер языка | Опытный рецензент | Отвечает за папку языка. Поддерживает глоссарий в актуальном состоянии. |
| Мейнтейнер | [@amaklakov-droid](https://github.com/amaklakov-droid) | Принимает новые языки. Сливает pull request. Принимает окончательное решение при разногласиях. |

Один человек может выполнять несколько ролей. Но рецензент не может одобрить
pull request, который открыл сам. GitHub не разрешает автору pull request
одобрить его.

## Файлы и папки

У каждого языка есть папка в `docs/`. Имя папки — код языка. Используйте код
в формате Best Current Practice 47 (BCP 47), например `ru`, `de` или `pt-BR`.

| Английский оригинал | Перевод |
| --- | --- |
| `README.md` | `docs/<lang>/README.md` |
| `docs/en/<name>.md` | `docs/<lang>/<name>.md` |

Имя файла перевода совпадает с именем английского оригинала. Статус каждого
языка показан в [LANGUAGES.md](../LANGUAGES.md).

## Заголовок i18n

Каждый перевод начинается с заголовка i18n. «i18n» — сокращение слова
«internationalization» (интернационализация). Заголовок — это HTML-комментарий,
поэтому GitHub не показывает его на странице.

```markdown
<!--
i18n:
  source: docs/en/usage.md
  source_hash: 1a2b3c4d5e6f
  status: draft
  translated_with: ai
  reviewed_by: []
-->
```

| Поле | Значение |
| --- | --- |
| `source` | Путь к английскому оригиналу от корня репозитория. Для файла, который не перевод, укажите `none` (см. [Глоссарий](#глоссарий)). |
| `source_hash` | Первые 12 символов хеша SHA-256 английского оригинала. Хеш вычисляет инструмент. Не меняйте его вручную. |
| `status` | `draft`: перевод ждёт проверки. `reviewed`: рецензент одобрил перевод. |
| `translated_with` | `ai`: первый черновик сделала AI-модель. `human`: первый черновик сделал человек. |
| `reviewed_by` | GitHub-имена рецензентов, например `[@amaklakov-droid]`. |

Не пишите заголовок вручную. Используйте команду `stamp` инструмента
`tools/i18n_status.py` (см. [Справка по инструменту](#справка-по-инструменту)).
«Отметить файл» значит записать или обновить его заголовок этой командой.

Инструмент сравнивает `source_hash` с хешем текущего английского оригинала.
Затем он присваивает каждому файлу одно из состояний:

| Состояние | Значение |
| --- | --- |
| `current` | Перевод соответствует текущему английскому оригиналу. |
| `outdated` | Английский оригинал изменился после последней отметки. Перевод нужно обновить. |
| `missing` | В папке языка нет файла для английского оригинала. |
| `untranslated` | Файл всё ещё содержит английскую копию, которую сделала команда `new`. |
| `invalid` | У файла нет заголовка, или в заголовке есть ошибка. |
| `standalone` | Файл — не перевод (`source: none`). Инструмент не учитывает его. |

## Процесс

Процесс состоит из восьми шагов. Каждому шагу посвящён раздел ниже.

### Шаг 1. Запросите язык

Новый язык может запросить любой человек.

1. Откройте форму
   [Request a documentation language](https://github.com/amaklakov-droid/controlled-language-skill/issues/new?template=language-request.yml).
2. Укажите название языка и его код BCP 47.
3. Напишите, кто будет читать документацию на этом языке.
4. Сообщите, можете ли вы проверить перевод как носитель языка.
5. Если вы знаете других возможных рецензентов, укажите их GitHub-имена.
6. Отправьте issue.

Мейнтейнер принимает язык, только если хотя бы один носитель языка согласен
проверить перевод. Если вы не носитель языка, сначала найдите рецензента.
Рецензентов можно искать в
[Discussions](https://github.com/amaklakov-droid/controlled-language-skill/discussions).

### Шаг 2. Примите язык

Этот шаг выполняет мейнтейнер:

1. Добавьте метку `lang:<lang>` в `.github/labels.yml`.
2. Запустите `tools/sync_labels.sh`, чтобы создать метку на GitHub.
3. Добавьте метку `lang:<lang>` к запросу.
4. Создайте папку языка:

   ```bash
   python3 tools/i18n_status.py new <lang>
   ```

   Команда копирует каждый английский оригинал в `docs/<lang>/`. В начало
   каждой копии она добавляет заголовок i18n со `status: draft`.
5. Добавьте папку `docs/<lang>/**` в `.github/labeler.yml`: в метку `i18n`
   и в новую метку `lang:<lang>`.
6. Добавьте папку и её рецензентов в `.github/CODEOWNERS`:

   ```text
   /docs/<lang>/ @amaklakov-droid @reviewer-handle
   ```

7. Добавьте рецензентов в список рецензентов в [LANGUAGES.md](../LANGUAGES.md).

Переводчик, который работает в форке, тоже может запустить команду `new` в
своём форке. Тогда мейнтейнер выполняет остальные действия в отдельном pull
request.

### Шаг 3. Сделайте черновик с помощью AI

Черновик делает переводчик. Для каждого файла в `docs/<lang>/` выполните
следующие действия:

1. Откройте файл. После заголовка в файле находится английский текст.
2. Скопируйте промпт ниже в AI-модель.
3. Замените в промпте заполнители в фигурных скобках.
4. Вставьте содержимое файла в конец промпта.
5. Замените содержимое файла результатом.
6. Убедитесь, что заголовок не изменился.

```text
Translate the Markdown file below from English into {LANGUAGE} ({CODE}).
The file is part of the documentation of "controlled-language", an agent
skill for technical writing.

Rules:
1. Keep the Markdown structure: headings, lists, tables, block quotes,
   blank lines, and HTML comments.
2. Keep the i18n header (the first HTML comment, which starts with "i18n:")
   exactly as it is.
3. Do not translate code blocks, inline code, commands, options, file
   names, paths, configuration keys, URLs, rule IDs (for example S2 or V3),
   or product names.
4. Keep the target of each link. Translate only the link text. If a link
   goes to a heading (the part after "#"), change that part to match the
   translated heading. GitHub makes this part from the heading text: lower
   case, hyphens in place of spaces, and no punctuation.
5. Keep UI labels in English when the product UI is in English.
6. Keep English example sentences that show the rules of controlled English
   in English. They are examples of English text.
7. In the language bar (the line of language links under the first
   heading), show {LANGUAGE} in bold without a link. Make "English" a link
   to the English page.
8. Translate all other text. For instructions, use the standard imperative
   form of {LANGUAGE} for technical documentation.
9. Write short sentences. Give one instruction in each sentence. If an
   English sentence is long, make two sentences.
10. Use one term for each concept in all files. Use the terms of the
    glossary. Do not use synonyms to make the text less repetitive.
11. Do not add, remove, or explain content. Do not add notes.
12. Do not write that the project is compliant with ASD-STE100, certified,
    or endorsed by ASD.
13. Output only the translated file. Do not put it in a code block.

Glossary (English term: {LANGUAGE} term):
{GLOSSARY}

File {FILE}:
```

Используйте промпт на английском для любого языка. Вместо `{GLOSSARY}` вставьте таблицу из
`docs/<lang>/glossary.md`. Если у языка ещё нет глоссария, напишите `none`.

Файл можно перевести и вручную. В этом случае перед открытием pull request
отметьте файл с параметром `--translated-with human`.

**Проверьте черновик с помощью skill.** Проверьте черновик skill
controlled-language на уровне 2. К тексту не на английском языке skill
применяет универсальные правила и языковой файл, если он есть. Например,
отправьте агенту такой запрос:

```text
/controlled-language 2
Review docs/<lang>/usage.md. The text is in <language>. Do not change code,
links, or the i18n header.
```

Исправьте проблемы, которые найдёт проверка. Не меняйте смысл текста.

**Проверьте статус.** Выполните команду:

```bash
python3 tools/i18n_status.py check
```

Каждый файл языка должен иметь статус `draft` и состояние `current`. Если у
файла состояние `untranslated`, в нём всё ещё английский текст.

### Шаг 4. Откройте pull request

1. Создайте ветку в своём форке, например `i18n/<lang>`.
2. Убедитесь, что в заголовке каждого файла указано `status: draft`.
3. Сделайте коммит файлов из `docs/<lang>/`.
4. Отправьте ветку в свой форк.
5. Откройте pull request с шаблоном для переводов. Чтобы выбрать шаблон,
   добавьте `?template=translation.md` к адресу страницы pull request:

   ```text
   https://github.com/amaklakov-droid/controlled-language-skill/compare/main...YOUR-USER:YOUR-BRANCH?expand=1&template=translation.md
   ```

   В адресе замените `YOUR-USER` на своё GitHub-имя. Замените `YOUR-BRANCH`
   на имя своей ветки.
6. Заполните чек-лист шаблона.
7. Добавьте метку `needs-native-review`.

Метки `i18n` и `lang:<lang>` добавляет автоматически workflow labeler. Если
вы не можете добавлять метки, мейнтейнер добавит `needs-native-review` за вас.

### Шаг 5. Проверьте перевод

Рецензент сравнивает перевод с английским оригиналом на GitHub.

1. Откройте pull request.
2. Нажмите **Files changed**.
3. Откройте английский оригинал файла во второй вкладке браузера.
4. Прочитайте перевод и сравните его с английским оригиналом.
5. Чтобы предложить изменение, нажмите кнопку **+** рядом со строкой.
6. В поле комментария нажмите кнопку предложения изменений. GitHub добавит
   блок `suggestion` с текстом строки.
7. Напишите правильный текст в блоке `suggestion`. Переводчик сможет принять
   предложение одним нажатием.
8. Если перевод правильный, нажмите **Review changes**.
9. Выберите **Approve**.
10. Нажмите **Submit review**.

Проверьте следующее:

- Смысл совпадает с английским оригиналом.
- Текст естественный и понятный для носителя языка.
- Инструкции написаны в стандартной повелительной форме языка.
- Термины соответствуют глоссарию.
- Код, команды, имена файлов, ссылки и заголовок i18n не изменились.

Мейнтейнер сливает перевод только после одобрения хотя бы одного рецензента
этого языка. Рецензенты перечислены в [LANGUAGES.md](../LANGUAGES.md) и в
`.github/CODEOWNERS`.

### Шаг 6. Отметьте перевод как проверенный

После одобрения переводчик или мейнтейнер выполняет следующие действия в
ветке pull request.

1. Проверьте состояние файлов:

   ```bash
   python3 tools/i18n_status.py check
   ```

> **ОСТОРОЖНО:** Отмечайте только файлы в состоянии `current`. Если вы
> отметите устаревший файл, инструмент покажет его как актуальный. Но в файле
> не будет последних изменений английского оригинала.

2. Установите статус `reviewed` и добавьте рецензента:

   ```bash
   python3 tools/i18n_status.py stamp docs/<lang>/*.md --status reviewed --reviewer @handle
   ```

3. Обновите таблицу статусов в [LANGUAGES.md](../LANGUAGES.md):

   ```bash
   python3 tools/i18n_status.py table
   ```

4. Если язык публикуется впервые, добавьте его в языковые панели. Языковая
   панель — это строка со ссылками на языки под заголовком каждой страницы.
   - В `README.md` и в каждом `docs/*/README.md` добавьте ссылку на
     `docs/<lang>/README.md`.
   - На каждой странице в `docs/en/` добавьте ссылку на ту же страницу в
     `docs/<lang>/`.
5. Сделайте коммит изменений.
6. Отправьте ветку.

### Шаг 7. Опубликуйте перевод

Мейнтейнер сливает pull request. Слияние и есть публикация перевода. GitHub
сразу показывает новые страницы. Других шагов выпуска для документации нет.

### Шаг 8. Обновляйте перевод

Когда английский оригинал меняется, его переводы устаревают. Их находит
workflow `.github/workflows/i18n-outdated.yml`. Он запускается после каждого
push в `main`, который меняет `README.md` или файл в `docs/`.

- Если перевод устарел, отсутствует или не переведён, workflow открывает
  issue «Translations are out of date». У issue есть метка
  `translation-outdated` и список файлов.
- Если issue уже открыт, workflow обновляет список.
- Когда все переводы актуальны, workflow закрывает issue.

Чтобы обновить перевод:

1. Найдите файл в issue «Translations are out of date».
2. Найдите изменения английского оригинала командой
   `git log -p -- docs/en/<name>.md`. Можно также посмотреть историю файла на
   GitHub.
3. Измените перевод, чтобы он соответствовал английскому оригиналу. В этом
   поможет AI-модель. Дайте ей английские изменения и текущий перевод.
4. Отметьте файл:

   ```bash
   python3 tools/i18n_status.py stamp docs/<lang>/<name>.md
   ```

   Команда записывает новый хеш. Если статус был `reviewed`, команда меняет
   его на `draft`: новый текст ещё не одобрил ни один рецензент.
5. Откройте pull request с шаблоном для переводов (шаг 4).
6. Получите одобрение рецензента этого языка (шаг 5).
7. Отметьте файл как проверенный (шаг 6).

Если вы меняете английский оригинал, не меняйте переводы на языках, которыми
не владеете. Workflow отметит эти переводы как устаревшие. Переводчик обновит
их позже.

## Глоссарий

У каждого языка может быть глоссарий: `docs/<lang>/glossary.md`. В глоссарии
указан перевод каждого важного термина. Благодаря глоссарию термины
одинаковы во всех файлах и у всех переводчиков.

Глоссарий — не перевод английского файла. В его заголовке указано
`source: none`. Инструмент не учитывает этот файл. Чтобы создать заголовок,
выполните команду:

```bash
python3 tools/i18n_status.py stamp docs/<lang>/glossary.md --source none
```

Используйте таблицу из трёх столбцов:

```markdown
| English | Русский | Примечание |
| --- | --- | --- |
| skill | skill | Не переводим, пишем латиницей. |
| checker script | скрипт проверки | |
| level | уровень | |
```

Соблюдайте правила:

- Добавляйте термин, когда переводите его впервые.
- Вставляйте глоссарий в промпт для AI (`{GLOSSARY}`).
- Если вы меняете термин, замените его во всех файлах языка в том же pull
  request.
- Записывайте причины решений в столбец «Примечание».

## Что не нужно переводить

Оставьте на английском:

- Заголовок i18n.
- Блоки кода и встроенный код.
- Команды, параметры и их значения.
- Имена файлов, пути и ключи конфигурации, например `non_english`.
- Адреса URL и цели ссылок. Меняйте только якоря переведённых заголовков.
- Идентификаторы правил, например `S2` или `V3`.
- Названия продуктов, проектов и стандартов: controlled-language,
  ASD-STE100, Simplified Technical English, Claude Code, GitHub.
- Надписи интерфейса, если интерфейс продукта на английском.
- Английские примеры предложений, которые показывают правила контролируемого
  английского. После примера можно добавить перевод.

Точно сохраняйте смысл правовых уведомлений. ASD-STE100 — товарный знак ASD
(Aerospace, Security and Defence Industries Association of Europe).
Проект не связан с ASD. Не пишите, что проект или его результаты
соответствуют ASD-STE100, сертифицированы или одобрены ASD.

## Разногласия между рецензентами

Два рецензента могут предпочесть разные переводы предложения или термина.
Действуйте так:

1. Обсудите варианты в pull request. Объясните причину каждого варианта.
2. Выберите вариант, который поймёт большинство читателей на этом языке.
   Предпочитайте стандартную форму языка региональной или редкой форме.
3. Если рецензенты не договорились, попросите мейнтейнера принять решение.
   Упомяните @amaklakov-droid в pull request.
4. Если разногласие касается термина, запишите решение в глоссарий.

Решение мейнтейнера окончательное. Мейнтейнер может попросить совета у
мейнтейнера языка.

## Как стать мейнтейнером языка

Мейнтейнер языка отвечает за папку одного языка. GitHub просит его проверить
каждый pull request, который меняет эту папку. Мейнтейнер языка также
поддерживает глоссарий в актуальном состоянии.

Чтобы стать мейнтейнером языка:

1. Предложите себя в рецензенты через форму
   [Volunteer as a native-speaker reviewer](https://github.com/amaklakov-droid/controlled-language-skill/issues/new?template=reviewer-signup.yml).
2. Проверяйте pull request с переводами на этот язык.
3. После двух или более проверок напишите мейнтейнеру в issue или в
   [Discussions](https://github.com/amaklakov-droid/controlled-language-skill/discussions).

После этого мейнтейнер выполняет следующие действия:

1. Добавляет ваше имя в строку папки языка в `.github/CODEOWNERS`.
2. Добавляет вас в [LANGUAGES.md](../LANGUAGES.md) как мейнтейнера языка.

## Языковые правила для skill

Skill применяет 32 универсальных правила ко всем языкам. **Языковой файл**
добавляет правила для грамматики одного языка. Например, русский файл
убирает отглагольные существительные и деепричастные обороты. Скрипт
проверки тоже читает таблицу замен из языкового файла.

Языковые файлы лежат в `controlled-language/references/languages/`. Имя
файла — код языка: `ru.md`, `de.md`, `pt-BR.md`.

### Как добавить языковой файл

1. Скопируйте `controlled-language/references/languages/_template.md`
   в `<код>.md`.
2. Опишите форму инструкций, слова-сигналы и правила. Дайте каждому правилу
   номер: код языка заглавными буквами и число (`DE1`). Свяжите каждое
   правило с универсальным правилом из `rules.md`.
3. Пишите пояснения на английском. Примеры пишите на самом языке.
4. Добавьте таблицу замен. Перечислите все формы слова, которые должен
   находить скрипт. Или напишите начало слова и `*`.
5. Проверьте таблицу на примере текста:

   ```bash
   python3 controlled-language/scripts/check.py --lang <код> --level 2 sample.md
   ```

6. Укажите в файле статус `draft`.
7. Откройте pull request. Запросите проверку у носителя языка.

Первый черновик файла можно сделать с помощью AI-модели. Дайте модели
`_template.md`, `ru.md` (как пример) и `rules.md`. Затем носитель языка
должен проверить каждое правило и каждый пример.

### Как проверить языковой файл

Носитель языка проверяет:

- Обычна ли форма инструкций для технических документов на этом языке?
- Обычны ли слова-сигналы для этого языка?
- Верно ли каждое правило для грамматики языка?
- Плохи ли примеры «Not» и хороши ли примеры «Use»?
- Есть ли у каждого слова из таблицы замен замена лучше? Нет ли у слова
  других значений, которые скрипт не должен отмечать?

После одобрения рецензент меняет статус в файле на `reviewed` и добавляет
своё имя на GitHub. Затем мейнтейнер добавляет файл в таблицу
в `controlled-language/references/languages.md`.

## Справка по инструменту

Инструменту `tools/i18n_status.py` нужен Python 3.8 или новее. Других пакетов
он не требует. Запускайте его из корня репозитория.

| Команда | Описание |
| --- | --- |
| `check` | Показывает статус каждого перевода. |
| `check --strict` | Дополнительно завершается с кодом 1, если какой-либо файл в состоянии `invalid`. |
| `check --github-summary` | Показывает статус в формате Markdown для сводки задания GitHub Actions. |
| `check --list-outdated` | Показывает по одной строке для каждого файла в состоянии `outdated`, `missing` или `untranslated`. Поля разделены табуляцией: состояние, код языка, перевод, английский оригинал. |
| `stamp FILE...` | Записывает или обновляет заголовок каждого файла. Устанавливает в `source_hash` хеш текущего английского оригинала. |
| `table` | Заново создаёт таблицу статусов в [LANGUAGES.md](../LANGUAGES.md). |
| `new LANG` | Создаёт папку `docs/LANG/`. Копирует в неё каждый английский оригинал и добавляет заголовок со `status: draft`. Если папка уже существует, команда завершается с ошибкой. |

Параметры команды `stamp`:

| Параметр | Описание |
| --- | --- |
| `--status draft`, `--status reviewed` | Устанавливает статус. Без этого параметра команда сохраняет статус. Но если английский оригинал изменился, команда меняет `reviewed` на `draft`. |
| `--reviewer @handle` | Добавляет рецензента в `reviewed_by`. Чтобы добавить нескольких рецензентов, повторите параметр. |
| `--translated-with ai`, `--translated-with human` | Устанавливает `translated_with`. Для нового заголовка значение по умолчанию — `ai`. |
| `--source PATH` | Устанавливает английский оригинал. Без этого параметра команда берёт его из заголовка или из пути к файлу. Для файла, который не перевод, укажите `--source none`. |

Все команды принимают параметр `--root DIR`. По умолчанию это родительская
папка `tools/`.
